# 项目协作守则

本文件承载仓库级协作规则。根目录 `AGENTS.md` 是入口，并特别标明 Electron 的沙箱外复测要求；用户在会话中给出的指令优先。

## 资料与变更

先读 `agent/architecture.md` 了解产品目标、目录边界和运行路径，再读 `agent/change-log.md` 了解至今的主要改动与实现方法。代码和 Git 历史是最终事实来源；文档若与代码不一致，应在同一次改动中更新。

每次改动项目结构、存储契约、运行方式或用户功能后，更新这两份现有文档中的相关内容。变更历史按功能聚合而非按时间流水追加：每项功能是一个一级列表项，后续进度写入该项的说明或子要点；尚未验收完成的功能项必须以“未完成”开头。每项说明简述“做了什么、为什么、如何实现、验证结果”，不要记录临时调试流水账。不要把测试产物、缓存、安装包或用户项目数据写进 `agent/`。

项目开发过程中可以在迁移入口、测试夹具和内部实现中使用版本号描述历史格式；一项功能完整交付后，面向用户的页面、文案、帮助和正常代码路径不得残留“v1 / v2 / v3”“旧版兼容”等中间态表述。格式、命名、接口或模型升级应一次性同步所有调用方，删除废弃实现和入口，只保留一套权威契约；迁移入口仅负责把历史文件升级为当前格式，不得成为长期双路径运行逻辑。实现时优先可复用、变量化的模型与组件，主动清理死代码和不再使用的设计。

## 开发预览与发布打包

在用户明确宣布当前版本可用于稳定发布前，不生成、保留或人工检查 Windows 安装包。开发预览和人工界面检查统一在沙箱外使用 `npm.cmd run dev`；常规回归按需要运行 `build`、`verify` 等检查。只有收到用户明确的发布确认后，才可运行 `npm.cmd run dist:win` 生成 `release/` 中的安装包，并执行安装包图标、离线资源和安装流程的验收。安装包属于可再生交付物，不得作为日常开发产物保留或提交。

开发前查看 `git status` 与最近提交。本项目只提供 Electron 桌面应用；Vite 仅作为桌面开发时的界面热更新服务，项目数据通过受限 IPC 写入用户指定目录。运行 `npm.cmd run build`、单元测试与必要的桌面端测试后再提交。提交不得包含 `.env`、`node_modules`、`dist`、`dist-electron`、`release` 或临时测试目录；未经用户明确要求不提交 commit。

## Git 提交信息规范

提交信息采用“类型 + 中文摘要 + 四段正文”的固定格式。现有历史提交已经使用这一结构；后续统一使用下面的字段名称，避免同一含义出现多套叫法。

```text
<type>: <一句中文摘要>

原因：说明用户问题、产品目标或工程动机。

内容：列出本次可观察的功能、界面、测试、配置或文档变化。

实现：说明关键模块、数据流、接口、样式策略或验证方式；只记录能帮助维护者理解的技术决策。

结果：列出实际执行的检查命令及结果，并明确剩余风险、未覆盖场景或阻塞条件。
```

`type` 使用最贴合主目的的类型：`feat` 新功能，`fix` 缺陷修复，`refactor` 重构，`docs` 文档，`test` 测试，`perf` 性能，`build` 构建，`chore` 工程维护。标题保持单一主题、简洁、无句号；正文使用事实和结果，避免记录临时调试流水或与项目无关的本机信息。

一次提交应围绕一个可验收主题组织。若改动同时涉及代码、测试和文档，把它们作为同一主题的不同内容列在正文中；若包含互不相关的功能，应拆分提交。提交前先检查 staged 与 unstaged 差异，只把本次主题相关的文件加入提交，并再次确认没有 `.env`、构建产物或测试临时目录。

本项目当前改动可使用以下格式作为提交说明：

```text
feat: 完成工作台交互升级与视觉规范收口

原因：统一工作台创作路径和视觉层级，补齐模式切换、媒体编辑、笔记与控件反馈中的可用性问题。

内容：完善项目、媒体、画布、笔记、拖放和模式切换交互；收敛画布、侧栏、主题选择器和样式预设；补充视觉方向、设计工作流、架构约束和端到端测试。

实现：重构 Electron/React 交互组件与共享 CSS token，统一控件状态和动效；将样式预设外框与内部预览拆分，避免重复线框；把外来技能改为用户级目录说明，不在仓库保留源码副本。

结果：`npm.cmd run build`、定向 Electron 端到端用例和 `git diff --check` 已通过；视觉截图已按验收流程复拍，剩余未覆盖状态在交付说明中列明。
```

## 任务完成与问题闭环

每个任务从接手到交付必须形成可追溯的闭环，不能只凭代码已修改或页面“看起来正常”宣布完成。

1. 明确目标与验收边界：把用户需求拆为可观察的结果、受影响的模块和必要的反例；先说明本轮不涉及的范围，避免把相邻功能的猜测当成任务目标。
2. 建立工作区基线：修改前检查 `git status`、相关文件、现有测试和最近提交。将本轮目标相关的差异与工作区既有差异分开记录；既有未提交改动默认归属原作者，不覆盖、不回退，也不得把它们计入本轮成果。
3. 复现并记录事实：用最小真实数据和稳定步骤触发问题，记录输入、环境、操作、期望与实际结果。日志、DOM 状态、保存结果、截图和测试失败信息属于事实；“可能是某处样式/逻辑导致”的判断属于待验证假设，二者必须区分。
4. 比对并定位根因：沿数据流、状态流和渲染/调用链比对目标行为与当前实现，检查配置、持久化状态、异步时序、环境偏好和既有回归。根因必须能解释已观察到的现象，并有代码、日志或可重复实验支撑；不能以压制症状的方式替代定位。
5. 实施单一且可维护的修复：优先修正权威数据源、共享逻辑或真正失效的边界；同步更新调用方、类型、测试和文档。每一轮只修改能检验同一假设的一组直接相关内容，避免用硬编码、临时开关、重复实现或兼容分支掩盖问题。
6. 按风险验证修复：先运行静态检查、构建或受影响模块测试，再运行能覆盖用户路径的最小集成/桌面用例。视觉与交互问题按 `agent/visual-verification.md` 在相同真实场景中复拍并比较；桌面 Electron 检查必须遵守沙箱外规则。验证需同时证明“问题已消失”和“相邻原有行为未回归”。
7. 形成如实结论：只有目标、根因修复和相应验证均完成，才能标记任务完成。交付时说明改动位置、验证命令及结果、保留的风险或未覆盖场景；未验证、无法复现、受外部条件阻塞或仅部分完成时，明确标为“未完成”，并写出下一步所需条件。
8. 归档长期知识：将稳定的功能结果补入对应的 `change-log` 功能条目；仅把可复用的流程、约束和验收标准写入协作守则或架构文档。不要把临时排查流水、屏幕截图或中间猜测写成项目事实。

## 桌面测试环境

`npm.cmd run verify` 包含 Electron 桌面端到端测试，不可在沙箱内运行。`npm.cmd run smoke`、`npm.cmd run test:e2e`、`npm.cmd run dev` 和 `npm.cmd start` 也只能在沙箱外运行。使用允许沙箱外执行的工具参数直接启动，或在宿主机 PowerShell 中从仓库根目录运行；不要把在沙箱里启动后再传出进程作为复测方式。

2026-11-16 的沙箱内失败日志记录 `GPU crashed -1073741515` 和 `launch-failed 49`。`-1073741515` 对应 `0xC0000135`，说明子进程装载依赖失败；目前没有证据确定具体 DLL 名称。沙箱外运行同版冒烟测试得到 `SMOKE_OK`。出现 `0x80000003` 弹窗时，先核对测试进程与 `userdata/runtime.log` 的时间、退出码和启动环境，再判断是否为应用代码问题。不要仅凭弹窗异常码推断缺失的 DLL。

## UI 资源与设计参考

- 开发新的图标时，优先在 [21st.dev Community Icons](https://21st.dev/community/icons) 中搜索和选择，重点关注 Lucide、Phosphor、Tabler、Remix Icon、Heroicons；按功能语义检索，并保持整个软件图标风格统一（线条粗细、尺寸、填充方式）。
- 开发新的主题、组件样式和颜色方案时，先按 `agent/ui-design-workflow.md` 从产品行为确定方向；方向确定后，可在 [21st.dev Community Themes](https://21st.dev/community/themes) 与 [21st.dev Components](https://21st.dev/community/components) 中寻找实现参考，并适配到本项目技术栈（React + Konva + 普通 CSS）。
- 使用前检查许可证、技术兼容性和设计一致性；保留必要的归属信息。参考 UI 应严格复现视觉与动画，不做简化。
- 颜色库以 Pantone 年度代表色为重要来源（见 `src/core/pantone.ts`），新增年度色时按对象结构追加并标注近似换算来源。

## 视觉截图验收

视觉任务按 `agent/visual-verification.md` 执行：先以真实内容创建可复现场景，在固定主题、缩放、窗口和交互状态下截取基线；依据布局、可见性、层级、材质、文字、动画与可访问性差异提出单一假设，做小范围修改后用相同条件复拍。默认覆盖静止/交互稳定帧、明暗主题与 Windows 100%／150% 缩放；桌面截图只能在沙箱外生成，产物写入 `test-results/` 且不提交。达到文档中的验收标准才可记录为已验证。
